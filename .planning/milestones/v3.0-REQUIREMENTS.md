# Requirements: Machine Maintenance — v3.0 The record

**Milestone:** v3.0 The record
**Status:** Defining — opened 2026-11-06
**Context:** v1.0 shipped the core, v1.1 made every entity operable, v2.0 gave it a
front door. All three are archived in `.planning/milestones/`. This milestone changes
what the application can *tell you*, not what it can store.

## Why this milestone exists

The app records everything a workshop needs and can only answer "what needs attention
now". After a month of use the question changes to "which machine keeps breaking, when
did we last touch it, and what is it costing me?" — and the app cannot answer any of it.

Three facts from the code (2026-11-06):

* `work_orders.closed_at` is stored on every finished job and **no screen shows a
  completed job or a date range**. The data is there; the view is not.
* `workOrderFilter()` understands `status`, `equipment_id` and `assigned_to`. There is no
  text search, so a machine can only be found by scrolling.
* There are **no hours and no costs anywhere**. A finished job is recorded as a job that
  happened, not as work that took four hours and consumed a bearing.

## Requirements

### HIST — History (Phase 14)

* **HIST-01** — Opening a machine shows **its own history**: every work order against
  it, opened and closed dates, owner, status — including jobs still open.
* **HIST-02** — A **History screen** lists completed jobs across all machines, newest
  closed first, with the machine they belong to.
* **HIST-03** — The history can be narrowed to a **date range** (closed between two
  dates, inclusive). A malformed date is refused with a readable message, not a 500.
* **HIST-04** — A machine with no jobs, a range with nothing in it, and a failed load
  are three different sentences — never an empty table.

### FIND — Find it (Phase 15)

* **FIND-01** — Free-text search over work orders (title, notes, machine name) and over
  machines (name, asset tag, location, category). Case-insensitive, partial match.
* **FIND-02** — Search composes with the existing filters: search + status + owner +
  date range in one query, not one at a time.
* **FIND-03** — The screen and the CSV export are built from **the same filter code**,
  so the file still matches what is on screen by construction.
* **FIND-04** — "Nothing matched your search" is distinct from "there is nothing here".

### COST — What it cost (Phase 16)

* **COST-01** — A work order records **labour hours**; negative or non-numeric input is
  refused with a message.
* **COST-02** — A job's parts cost is the sum of the parts used on it, and its labour
  cost is hours × a single configured hourly rate. Both are shown per job.
* **COST-03** — A **Report screen**: choose a month, see jobs closed, hours, parts cost,
  labour cost, total, and the machines that failed most often.
* **COST-04** — The report exports as CSV that opens in Excel, from the same query that
  drew the screen.

## Out of scope (unchanged from PROJECT.md)

Camera/QR scanning, kanban, email/push notifications, React or a build step, PWA,
multi-tenancy. Photos of a fault were considered for this milestone and rejected: file
storage needs its own backup story, which belongs with the audit work, not here.

## Accepted cost

Two new screens (`history`, `report`) and one dialog, all in their own files. The work
order list gains two columns. `server.js` is already 737 lines, so **every new endpoint
goes in a route module rather than growing it further** — that is a prerequisite of this
milestone, not a nicety.

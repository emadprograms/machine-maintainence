# Plan 11-02: Role filtering, keyboard access, proving nothing moved

## Threat Model

| ID | Threat | Severity | Mitigation | Verified by |
|---|---|---|---|---|
| T-11-04 | The sidebar lists a screen the role cannot open, inviting a 403 and training the user to distrust the nav | **high** | Filtering uses the same `adminOnly` flag `PAGES` already carries, and the server remains the enforcement point | 11-02-01 |
| T-11-05 | Hiding a link is treated as access control | **high** | Both admin routes keep their 403 assertions; the sidebar is presentation only | 11-02-02 |
| T-11-06 | Keyboard users lose access to navigation that the tab row allowed | medium | Entries are buttons in a nav landmark; the toggle is focusable; focus ring is visible | 11-02-03 |

## Tasks

### Task 1: Role filtering

`renderShell` receives the signed-in user and filters `PAGES` on the existing
`adminOnly` flag — the same filter `buildTabs` used. A technician sees five
entries; an admin sees seven.

**Acceptance:** signing in as a technician renders five entries and neither
"Users" nor "Backup" appears in the markup.

### Task 2: Keyboard and focus

Entries are `<button>` elements inside `<nav aria-label="Sections">`. The toggle
carries `aria-expanded` and `aria-controls`. A visible `:focus-visible` ring is
added — the current stylesheet removes nothing, but it also defines nothing, so
the browser default is what exists today and must be kept deliberately.

**Acceptance:** tabbing from the header reaches the toggle, then every entry, in
visual order; each shows a focus ring.

### Task 3: Prove the screens did not move

The point of NAV-04. The suite already asserts every screen's behaviour
(85+ checks). This task adds explicit assertions that the ids the loaders write
into still exist in the markup, so a shell change that orphaned a screen fails
loudly:

- every `data-page` value in `PAGES` has a matching `<section data-page="...">`
- every loader function named in `showPage`'s map exists
- the sidebar's page keys are exactly the section keys — no entry without a
  section, no section without an entry (for an admin)

**Acceptance:** removing a section, or renaming a loader, fails a specific test.

## Notes

The suite cannot render DOM. The rendered checks in this phase are therefore
done once by hand and recorded in the verification report, while the durable
assertions are structural. That gap is stated rather than papered over.

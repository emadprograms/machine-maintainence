# Plan 12-02: The dashboard screen

## Threat Model

| ID | Threat | Severity | Mitigation | Verified by |
|---|---|---|---|---|
| T-12-04 | Titles and part names are interpolated into `innerHTML` unescaped | **high** | Reuse the existing `esc()` helper on every field, as every other renderer does | 12-02-03 |
| T-12-05 | A failed fetch renders as four zero cards, telling the user the workshop is idle | **high** | Error and empty are different states in the markup; a failed load says so and offers retry | 12-02-02 |

## Tasks

### Task 1: `public/dashboard.js`

Exports `renderDashboard(container, data)` and owns its own card markup. Separate
file: the same readability reason as the shell.

Each card: a label, a large count, up to five item rows, and a link to the
owning screen. Empty state is written per card — "No work orders open. Nothing
needs doing." — never a bare zero.

### Task 2: Wire it as the landing page

- `PAGES` gains `{ key: 'dashboard', label: 'Dashboard' }` first, and its section
  is added to `index.html` before Due soon
- `showPage('due')` on sign-in becomes `showPage('dashboard')`
- A loader `loadDashboard()` fetches the endpoint and renders
- The failed-load state is rendered by the loader's catch, not left blank

**Acceptance:** after sign-in the dashboard is visible with four cards.

### Task 3: Assertions

- `dashboard.js` exists and is not part of `app.js`
- `PAGES` contains a `dashboard` key and the markup has its section (the existing
  correspondence assertions cover this automatically once added)
- the landing call names `dashboard`, not `due`
- the renderer uses `esc(` on interpolated values
- the loader distinguishes empty from failed (both strings present in source)

**Acceptance:** each fails when removed.

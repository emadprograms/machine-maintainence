# Plan 12-01: The dashboard endpoint

## Threat Model

| ID | Threat | Severity | Mitigation | Verified by |
|---|---|---|---|---|
| T-12-01 | The endpoint leaks user data to a technician because it aggregates broadly | **high** | Four fixed sections; no users table is read at all; asserted by key shape and by payload scan | 12-01-03 |
| T-12-02 | A summary query forgets a filter the list applies, so the card disagrees with the screen | **high** | Reuse `workOrderFilter` and the parts predicate rather than writing parallel SQL | 12-01-02 |
| T-12-03 | The payload grows with the data (returning every low-stock row) | low | Items capped at 5; the count is separate and unbounded | 12-01-01 |

## Tasks

### Task 1: `GET /api/dashboard`

Returns:

```
{
  work_orders: { count, items: [{id,title,equipment_name,priority,status}], href: '#work' },
  due_soon:    { count, items: [{id,task,equipment_name,next_due,days_left}], href: '#due' },
  low_stock:   { count, items: [{id,name,qty,reorder_level}], href: '#parts' },
  machines:    { count, items: [{id,name,status}], href: '#equipment' }
}
```

- `work_orders` — status not `done`, ordered by priority then age
- `due_soon` — the same 7-day window and date arithmetic as `/api/pm/due`
- `low_stock` — `qty <= reorder_level`
- `machines` — status `down`
- every list capped at 5; `count` always the true total

Registered behind the session gate like every other read.

**Acceptance:** with an empty database all four counts are 0 and lists empty.

### Task 2: Assertions

- all four keys present with `count` and `items`
- each `href` names a screen that exists in `PAGES`
- items never exceed 5 while `count` reflects the true total (seed 7 low-stock parts)
- a technician's payload contains no `email`, no `password`, no user fields
- an anonymous request is 401
- the work-order count matches `GET /api/work-orders?status=open` length

**Acceptance:** each assertion fails when its section is broken.

# Plan 13-02: Rows, empty states and destructive actions

## Threat Model

| ID | Threat | Severity | Mitigation | Verified by |
|---|---|---|---|---|
| T-13-04 | An empty state is built by interpolating a record field (stored XSS in a new place) | medium | Empty states are static sentences; asserted to contain no interpolation | 13-02-03 |
| T-13-05 | An empty state replaces a genuine error, hiding a failure | **high** | The loader only renders the empty row on a successful fetch with zero rows; the catch path is unchanged | 13-02-02 |

## Tasks

### Task 1: Row treatment

CSS only, applied once: `.table td` padding and border, `tbody tr:hover`,
`.cell-strong` for the first column, `.cell-muted` for secondary text,
`.cell-num` right-aligned with tabular numerals. Then a pass over the seven
loaders to wrap first-column values in `cell-strong`, absent fields in
`cell-muted` (rendered as "Not set" rather than "—"), and money/quantities in
`cell-num`.

### Task 2: Empty states

A shared `emptyRow(colspan, sentence)` helper in `app.js`, called from each
loader when the fetch succeeds and returns nothing. Sentences say what the empty
state *means* and what to do: "No machines yet. Add the first one to start
tracking maintenance."

### Task 3: Destructive actions

Delete buttons confirm with the record named and the consequence stated:
`Delete "Lathe"? Its work orders and maintenance history go with it.`

## Acceptance

Each assertion fails when its behaviour is reverted.

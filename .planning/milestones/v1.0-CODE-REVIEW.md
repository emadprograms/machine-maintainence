## Verdict

**Do not build on this repo. Rebuild from scratch, but cheaply — and copy three things from it (the SQL schema, the scrypt password helper, and the visual design).**

The repo is not the problem you think it is: it actually *does* save to disk, it *does* hash passwords with scrypt, and its routes use parameterised queries. The problem is that everything around those good bones is shaped for a 48-hour online demo: a layered TypeScript stack you said you don't want, a data layer that rewrites the whole database file on **every** request (including plain page views), three parallel copies of the same frontend auth logic of which one is dead and one is broken, three overlapping copies of the "user" concept, and **zero tests**. On top of that I found two live security holes (a hardcoded signing secret that lets anyone mint an admin login, and a public sign-up endpoint that hands out a manager account) plus a documented startup path that **crashes on a clean machine** [ran].

For your specific goal — one beginner, no React/TypeScript, Windows, offline, SQLite, recurring maintenance — a stack of two files (`sqlite3` + `Express` in plain JavaScript, one HTML page) is roughly 600–900 lines and you can read all of it. Porting this repo to that shape means deleting more than half of its ~7,000 lines and rewriting the data layer anyway. The parts worth keeping are small enough to copy in an afternoon.

## 1. Data persistence (sql.js) — **Okay, with one real landmine**

**Short answer: yes, it writes a real file on disk, after every single write — and also after every read. Data survives a crash. But a power cut during a save can leave a corrupt file with no backup, and the file location is barely configurable.**

| Question | Answer |
|---|---|
| Does it write to disk? | Yes, real file, full SQLite format. **[read]** `backend/src/database.ts:377-381` (`db.export()` → `fs.writeFileSync(dbPath, buffer)`). Verified: I created an equipment record and the `.db` file appeared and grew. **[ran]** |
| When? | After **every** call to `execute()` — i.e. every INSERT/UPDATE/DELETE, *and* every login and page load, because `touchLastSeen()` writes `UPDATE users SET last_seen_at…` on each authenticated request (`backend/src/middleware/authGuard.ts:19-21,28`). **[read]** |
| Crash safety? | Good against a process crash/Ctrl-C: I created a record, `kill -9`'d the server, restarted it, and the record was still there. **[ran]** |
| Power-cut safety? | **Weak.** It writes straight over the live file with no temp-file-then-rename and no backup. I truncated the `.db` to simulate a half-finished write and the app then **refused to boot** with `database disk image is malformed` — no recovery, no backup, all data gone. **[ran]** |
| Path configurable? | Only partly. There is an env var `MAINTAINX_DB_PATH` (`database.ts:15`), but `start.sh` never sets it and there's no `.env` support; the default path is strange (see below). **[read]** |
| Backup / export? | None. No download, no scheduled copy. **[read]** |

### The three persistence problems worth knowing

**(a) It does not "save when it should" — it saves on every request, including reads. [ran]**
`execute()` ends with `saveDb()` (`database.ts:404-411`), so *any* statement triggers a full `db.export()` + `writeFileSync`. And `requireAuth` calls `touchLastSeen()` on **every** authenticated request (`authGuard.ts:19-21,28`), which is itself an `execute()`. I measured it: **five plain `GET /api/equipment` calls rewrote the 112 KB database file five times.** 50 reads = 50 disk writes. On one user's laptop that's merely wasteful; on a shared shop-floor PC with several tabs open, plus the notifications poller running every 30 s per browser tab (`hooks/useNotifications.ts:29`), plus `useAutoRefresh`, you get a continuous write stream on the system drive. Since images are stored *inside* the database as base64 (§2), the file grows with every photo, so the cost grows with use: at 1.4 MB a single page view rewrites 1.4 MB. **[ran]**

**(b) A crash mid-write can destroy everything (no atomic write, no backup). [ran]**
`saveDb()` writes the whole file **in place**, not to a temp file followed by an atomic rename, and there is no `.bak`. A power cut or Windows reset during a save leaves a half-written file and the app then cannot start at all: I truncated the file by half, restarted, and got `Error: database disk image is malformed` from `initDb` with no recovery path. Since a save happens on every request, and the file is large whenever photos exist, the window for this is not theoretical. The failure mode is "the whole maintenance history is gone, permanently, silently". **[ran]**

**(c) The database path is configurable, but not from anywhere the user can reach. [read]**
`MAINTAINX_DB_PATH` is read (`database.ts:15`) and honoured by `deploy.sh:19`, but `start.sh` never sets it and there is no `.env` loading anywhere, so on Windows the user has no supported way to put the database on a shared or backed-up drive. The fallback path is also odd: `path.join(backendDistDir(), '..', 'maintainx.db')` (`database.ts:12-14`) puts it **inside the code folder**, and `backendDistDir()` walks up to the first directory containing `bootstrap.js` (`lib/paths.ts:6-27`). In dev mode there is no `bootstrap.js`, so it falls back to `cwd/backend/dist`, producing `backend/backend/maintainx.db` when launched from `backend/`, and `backend/maintainx.db` when launched from the repo root. I saw **two different database files created by the same app**, depending on which command started it. **[ran]** That's the worst possible property for a data file: it silently depends on how you launched the program.

**Bonus, same class of risk:** the serverless branch sends the database to `/tmp` (`database.ts:9-14`), which is why the README's own Netlify demo resets on every cold start (`README.md:127`). Not your deployment, but it's the same architectural flaw and it's evidence the authors knew persistence was fragile.

## 2. Auth and security — **Problem** (two verified break-ins)

The *cryptography* is fine. The *policy* is not.

### What is done well
* Passwords are hashed with **scrypt** + random salt, self-describing format `scrypt$salt$hash`, compared with `timingSafeEqual` — the right primitives (`backend/src/lib/auth.ts:9-32`). **[read]**
* Plaintext passwords left over from the hackathon are migrated to hashes on startup (`database.ts:350-362`). **[read]**
* Tokens are signed and expire after 12 h (`lib/auth.ts:4,52-72`). **[read]**
* API routes are protected: `/api` is behind `requireAuth` except login/register/health (`backend/src/app.ts:19-31`). Unauthenticated `GET /api/equipment` correctly returns 401. **[ran]** Role checks exist on the sensitive routes (`admin.ts:9`, `equipment.ts:24,43,67`). **[read]**
* SQL is parameterised everywhere I checked — no string-concatenated user input. **[read]** The only SQL built by concatenation is `ensureColumn(table, …)` (`database.ts:364-375`), and its arguments are internal constants only. **[read]** Path traversal on `:id` is not exploitable because every query binds the value. **[read]**
* File-upload middleware (`multer`) is declared but **never used**; images arrive as base64 JSON strings. So there is no upload-directory traversal risk. **[read]**

### What is broken

**🔴 1. A hardcoded fallback secret lets anyone forge an admin login. [ran]**
`backend/src/lib/auth.ts:3` — `const SECRET = process.env.AUTH_SECRET || 'maintainx-pro-dev-secret-change-me';`
Nothing in `start.sh`, `deploy.sh` or the README sets `AUTH_SECRET`, so on a default install the signing key is a **public string in the repo**. I used it to sign a token claiming `role: "admin"` and got `HTTP 200` from `/api/admin/users` and `HTTP 201` creating a new admin account — with no such user existing in the database. That account then logged in normally. **[ran]** Anyone who has ever seen this repo has your admin panel. A signature is only as good as the secret, so this makes the whole login system decorative.

**🔴 2. Public self-registration hands out a manager account. [ran]**
`POST /api/auth/register` accepts `role` from the request body and allows `technician`, `manager` and `client` (`backend/src/routes/auth.ts:9,34`). I registered a brand-new account with `role: "manager"` and it immediately succeeded at `PUT /api/equipment/:id` (200) — i.e. anonymous internet users can edit your machines. Only `client` is held for approval; only `admin` is blocked. **[ran]** On the frontend, `pages/Register.tsx` (a form asking for an "admin registration key") is **not reachable** — it isn't imported in `App.tsx` — the live form is inline in `pages/Login.tsx`, and `admin_key` is silently ignored by the backend. **[read]**

**🔴 3. Any user can read every employee's data. [ran]**
`routes/users.ts:6-9` returns **all** users to **any** logged-in user (including a self-registered `client`) — names, emails, roles. A new manager account got `HTTP 200`. **[ran]** Same pattern in the pending-registrations endpoint: `admin.ts:115-123` selects `u.*`, which includes the **password hash column**. **[read]**

**🟠 4. Tokens are not revoked by "log out" and not checked against the database. [read]**
`requireAuth` (`middleware/authGuard.ts:24-30`) only verifies the signature; it never loads the user. So a suspended or deleted user keeps full access for up to 12 hours, and there is no logout endpoint at all (`lib/auth.ts` has no revocation list; the `sessions` table at `database.ts:60-66` is created but used by nothing). **[read]**

**🟠 5. Two factor-checking systems, one of them dead. [read]**
There are two files called almost the same thing: `middleware/auth.ts` (database-session based) and `middleware/authGuard.ts` (signed-token based). Only `authGuard.ts` is imported anywhere; `middleware/auth.ts` and the `sessions` table are dead code. This matters to you because when you go looking for "how does auth work" you will find the wrong file first.

**🟠 6. Demo credentials shipped in the UI. [read]**
`pages/Login.tsx:7-12` and `:203` list four demo accounts and the password `demo1234`, and one click fills the form. `backend/src/seed.ts:14-24` creates those accounts on first boot with that same hash. Fine for a hackathon jury; on a factory machine it is a permanent back door.

**🟡 7. Input is validated only loosely.** **[ran]**
* `PUT /api/equipment/:id` with `health_score: 999` or `status: "nonsense"` → **HTTP 500**, not a friendly 400. The database `CHECK` constraints reject it but nothing catches the exception. **[ran]**
* `POST /api/faults` with a non-existent `equipment_id` → **HTTP 201**, writing an orphan fault that no page can display. **[ran]**
* `express.json({ limit: '50mb' })` (`app.ts:17`) means a single request can be 50 MB of base64 images. I stored a 1.4 MB image in one call and the DB file grew to 1.4 MB — and since the whole file is rewritten on every request, that size now taxes every page view. **[ran]**
* Anomalies I did **not** verify: no rate limiting on `/login`, no `X-Frame-Options`/CSP headers, and no `Trust` proxy configuration — treat these as unconfirmed risks.

## 3. Code quality — **Okay at file level, poor at architecture level**

### The good
* Consistent file layout: `routes/`, `lib/`, `middleware/`, `pages/`, `components/`. Each route file is small (17–295 lines) and readable. **[read]**
* TypeScript is `strict` (`backend/tsconfig.json:8`), and the frontend **actually compiles** (`tsc -b` passed with no errors). **[ran]**
* No `TODO`/`FIXME` markers and no `console.log` litter in frontend code. **[read]**
* No SQL injection, as noted above.

### The problems

**🟠 Duplicated and dead code.** **[read]**
* **Three auth implementations in the frontend.** `context/AuthContext.tsx` (the real one, imported by 12 files), `hooks/AuthContext.tsx` (an older version, imported by exactly one file — `pages/Register.tsx`) and `services/api.ts`, which contains *two* token mechanisms side by side: `authHeaders()` reads `'maintainx.token'` (line 5) while `getToken()` reads `'token'` (line 18), and the `request()` function computes a token and then never uses the header it built (lines 22-29). **[read]** It happens to work because `authHeaders()` wins, but this is the single most common source of "why am I randomly logged out" bugs.
* `pages/Register.tsx` is a **dead page** (never imported) that is also **broken**: it calls `register(name, email, password, role, adminKey)` with five arguments while the hook it imports takes one object (`hooks/AuthContext.tsx:16`). **[read]**
* `middleware/auth.ts` + the `sessions` table: dead. `multer`: declared, never used. `hooks/AuthContext.tsx`: obsolete. Three copies of six stock photos (`Pictures/`, `frontend/public/pictures/`, `frontend/dist/pictures/` — ~55 MB of JPEGs in Git for a maintenance app). **[read]**

**🟠 Three overlapping models of "who is a user".** **[read]**
`users.company_id`, a `role = 'client'`, *and* a separate `companies` table all describe the same idea, and each screen mixes them differently. A concrete symptom: a `client` account that reports a fault stays `reported_by`-invisible to its own company, and there are two divergent permission checks — `context/AuthContext.tsx:21-26` has a `PERMISSIONS` table, while the backend enforces role strings in `requireRole`. If you keep this and add one field, expect to touch 4–6 files (see §5).

**🟠 One concept, four sources of truth.** **[read]**
The fault workflow exists as: a SQL `CHECK` constraint (`database.ts:91`), a TypeScript union (`types/index.ts:55`), an array of 7 statuses (`lib/faultWorkflow.ts:3-11`), a French label map (`types/index.ts:107-115`), and a second label map inline in the route (`routes/faults.ts:139-142`). Adding one status to "work order" means editing five places or the app breaks silently.

**🔴 No tests at all.** **[read]** No test framework in any `package.json`, no `*.test.*`/`*.spec.*` files, no CI (`.github` doesn't exist). For a beginner, the practical cost is that you have no safety net when you start deleting the 60% of this app you don't want.

**🟠 Migrations run on every startup, and some are destructive/demo-flavoured.** **[read]**
`runMigrations()` (`database.ts:145-167`) runs 12 steps at every boot. Two are wrong for production:
* `migrateExplicitImages()` **overwrites the `images` column of every fault and piece of equipment** with stock photos from `explicitImages.json` whenever the catalog `version` changes (`database.ts:204-238`). If your users uploaded a photo, a future edit to that JSON silently replaces all their photos.
* `migrateMaintenanceDates()` writes fake `last_maintenance` dates into every record that has none (`database.ts:195-202`) — invented history in a maintenance system. Note this is the only "maintenance" logic in the backend.

**🟡 Unhandled errors return 500 with a stack in the server console.** There is no Express error-handling middleware; `start().catch(console.error)` (`index.ts:36`) catches only startup errors. **[read]**

**One thing that is *not* a bug, since it looks like one:** `migrateUserRoles()` (`database.ts:240-273`) is not dead code; it is a guarded table rebuild for an earlier schema. It will do nothing on a fresh database. **[read]**

## 4. Windows and offline — **Problem**

**TL;DR: the "one-click" launcher is a bash script that doesn't work on Windows; the documented manual path crashes on a clean install; and the UI pulls fonts and photos from the internet.**

**🔴 `start.sh` is bash-only.** **[read]** 37 lines: `#!/usr/bin/env bash`, `set -euo pipefail`, `trap cleanup SIGINT SIGTERM`, `&`, `wait`. It will not run in `cmd.exe`. Git Bash can run it, but then `npx tsx src/index.ts &` + `wait` + signal traps are the flakiest part of Git Bash on Windows. There is no `.bat`/`.ps1`, no Docker file, no service definition.

**🔴 The manual path in the README crashes on a clean copy. [ran]**
README line 52 says `cd backend && node_modules/.bin/tsx src/index.ts`. I did exactly that on a fresh clone: the server dies with `Error: explicitImages.json introuvable` (`lib/imageCatalog.ts:23`). Cause: `loadImageCatalog()` looks in `backend/dist/data/` (only produced by a build) and at `$(cwd)/frontend/src/data/...` — which resolves to `backend/frontend/src/...` when you start from `backend/`. **[read]** Running `npm ci && npm run build` in `backend` first does not fix it either. **[ran]** I also ran `./start.sh` on a clean copy: the *same* error, and the script still prints "Projet lancé sur http://localhost:3001" while the backend is already dead, so `Ctrl-C` is the only thing keeping the terminal open. **[ran]** Net effect: **there is no documented path that starts this app on a fresh machine** (it only works if you happen to launch from the repo root, a path none of the docs mention). **[ran]**

**🟠 Password-protected HTTP (no `--insecure`) is not supported, and on a LAN the browser will refuse camera access.** The backend listens on `0.0.0.0:3001` (`index.ts:29`) over plain HTTP, and the README notes the camera needs a secure context (`README.md:108`) — on `http://192.168.x.x` the scan module cannot get the camera. **[read]** Relevant even if you drop the scanner: Web Push (for maintenance reminders) also requires HTTPS. If you later need "remind me when a PM is due", plain HTTP will block browser notifications — you'd need e-mail/Windows toast/desktop app instead, or a local certificate. **[read; needs confirmation on your exact setup]**

**🟠 There is no packaging at all.** No Electron, no `pkg`, no service install; `deploy.sh:16` just runs node in the foreground after a build. **[read]** Nothing here is copy-and-run on a Windows box that has no internet.

**🟡 `node_modules` cannot be copied between machines as-is. [read]**
I checked both lockfiles: the frontend pulls platform-specific binaries — `@rollup/rollup-win32-x64-msvc`, `@rollup/rollup-linux-x64-gnu`, 24 variants of `@rollup/rollup-*`, plus `@swc/core-*` and `esbuild` (the backend too, 8 `@esbuild/*` variants). These are prebuilt, not compiled — so **an offline `npm ci` from a USB stick does work** provided the USB copy was made on Windows (or you run `npm ci --include=optional` for both platforms). But dragging an existing `node_modules` from Linux/macOS, or from a different CPU type, will fail with an unhelpful "cannot find native binding" error. **[read; the cross-machine copy itself is not verified — I have no Windows box]**
*Practical consequence:* `sql.js` (the database) is **WebAssembly, not a native module** — that is genuinely good news for portability: nothing to compile with Visual Studio Build Tools, no `node-gyp`, no Python. **[read]** If you rebuild, `better-sqlite3` *would* introduce a native module and this problem; SQLite via `node:sqlite` (built into Node 22+) or `sql.js` avoids it. `multer` is unnecessary here anyway since it's unused. **[read]**

**🟠 Things fetched from the internet at runtime. [read]**
* **Google Fonts** — `@import url('https://fonts.googleapis.com/css2?family=Inter…')` at `frontend/src/index.css:1`. On your network the request just hangs and falls back to a system font; cosmetic, not fatal.
* **Unsplash photos** — ~70 occurrences of `https://images.unsplash.com/...` in `frontend/src/data/explicitImages.json` and `backend/src/data/explicitImages.json`. Those are the *default* images for every piece of equipment and every fault, so an offline install shows broken images everywhere. Cheap to fix (delete the images feature or bundle 6 local JPEGs).
* **sql.js WASM** — `database.ts:19-28` has a `locateFile` fallback to `https://sql.js.org/dist/…`, but *only* when it detects a serverless environment (`isServerless`, line 9-11). On Windows it uses the local `node_modules` copy. So this one is not an offline risk in your setup. Good.
* **Netlify-specific code** that you'd delete: `netlify.toml`, `netlify/functions/api.ts`, `@netlify/functions` + `serverless-http` in the root `package.json`, and the `VERCEL`/`NETLIFY`/`AWS_LAMBDA_FUNCTION_NAME` branch that sends the DB to `/tmp` (`database.ts:9-14`). Not harmful on Windows, purely dead weight — and that `/tmp` branch is why the README's own demo loses data on Netlify (`README.md:127`). **[read]**

**🟡 PWA service worker caches `/api` responses.** `vite.config.ts:26-37` registers a `NetworkFirst` runtime cache for `/api`. On a local server this can serve a stale page ("I saved it but it still shows the old value") for up to 10 minutes, and the "autoUpdate" worker adds its own surprises. For a single-machine LAN app, remove the PWA plugin; it buys you nothing. **[read]**

## 5. Ease of modification — **Problem** (the deal-breaker for you)

You said how easy it is to change matters more than features. This is where the repo scores worst, not because the code is bad but because of how much is wired together.

**Add a new field to machines (e.g. "serial number").** You must touch: `database.ts` (table definition ~line 69, *plus* an `ensureColumn()` line ~146 for existing DBs), `routes/equipment.ts` (the `INSERT` list line 29-31 and the `UPDATE` list line 43-61 — both enumerate columns by hand), `frontend/src/types/index.ts:10-23`, and the form in `pages/EquipmentList.tsx`. If the field is shown on the dashboard, also `routes/dashboard.ts`. **≈5 files, 7 edits, in two languages, with a database migration.** And a mistake in the routes file is a silent 500, because there is no test and no error handler. **[read]**

**Add a new page (e.g. "Recurring maintenance").** `pages/NewPage.tsx` → import + `<Route>` in `App.tsx` (two separate places: lines 6-28 and 70-99) → add to the correct role array in `lib/navigation.ts:35-83` (there are four separate hand-written nav lists, one per role) → add the API method in `services/api.ts:40-127` → if it needs a role, wrap in `<RequireRole>` and remember the backend check too. **≈5 files.** Doable with AI help, but every step is TypeScript-only and invisible to you when it's wrong — the compiler will complain about a missing icon type rather than tell you what you meant.

**Recurring preventive maintenance with due dates and reminders — this does not exist, and the two things that look like it are fake.** **[read]**
* `pages/technician/MaintenanceCalendar.tsx:34-39` **invents** maintenance dates by hashing the equipment's ID (`hashDay()`): the same machine gets a different "planned maintenance day" in every calendar month, and past-dated events are labelled "overdue" based on health score (`:61, :82`). It looks convincing and is meaningless. **Delete it; do not fix it.**
* `last_maintenance` is used in exactly one place, a fixed "+30 days follow-up" (`MaintenanceCalendar.tsx:65-87`), and otherwise only written by the fake-history migration (`database.ts:195-202`). There is **no** interval, frequency, recurrence or due-date column anywhere in the schema (`database.ts:48-136`). **[read]**
* "Reminders" = an in-app activity feed (`routes/notifications.ts`), 50 rows, no scheduling, no e-mail, no push. The `activities` CHECK constraint allows `'maintenance_due'` but nothing ever creates one. **[read]**

So this core requirement is a **green-field feature in both options** — the only difference is that here you'd be adding it to a schema you don't fully understand, and in a rebuild you'd add it to 40 lines of SQL you wrote yourself. That is a strong argument for the rebuild.

**What's safe to delete:** `pages/Register.tsx` (dead), `hooks/AuthContext.tsx` + `pages/Login.tsx`'s inline register mode (duplicate), `middleware/auth.ts` + `sessions` table (dead), `multer` + `@types/multer` (unused), `netlify/` + `netlify.toml` + `@netlify/functions` + `serverless-http` (Netlify only), `pages/Sites.tsx` + `lib/siteLayout.ts` (a static SVG "digital twin" toy, no links to real data beyond colour), `pages/Scan.tsx` + `components/scan/` + `lib/diagnostic.ts` (the "AI" is a regex over the equipment name — `diagnostic.ts:20-63` — and confidence is arithmetic on the number of photos, `:92`), `components/ui/Chatbot.tsx` + `lib/chatbot.ts` (keyword replies), `pages/KanbanBoard.tsx` + `@hello-pangea/dnd` (can be replaced by a status dropdown), `docs/` and the 55 MB of duplicate photos. **That's more than half the app.** **[read]** Which raises the obvious question: if you delete half and rewrite the data layer, what did you keep?

**The one genuinely valuable parse:** some of these features are **not** "fake", in the sense of broken. The scanner is a real `getUserMedia` capture flow, the Kanban is a real drag-and-drop board, the "3D twin" is a real (if crude) SVG projection. They're just irrelevant to *your* brief and expensive to maintain. Judge them as "not needed", not "bad".

## Top issues to fix first (if you were to keep it)

Ordered by "would I get burned by this in the first month" for *your* deployment:

1. **Set `AUTH_SECRET`** to a long random value (`lib/auth.ts:3`), and stop using the default. Otherwise every install is world-admin. 30 min.
2. **Delete or lock down public self-registration** (`routes/auth.ts:15-56`; also remove the register mode from `Login.tsx`). Allows anonymous manager accounts. 30 min.
3. **Fix startup for a clean/Windows machine**: make the seed resilient to a missing `explicitImages.json` (`lib/imageCatalog.ts:23`), and ship a `.bat` instead of `start.sh`. Otherwise the app literally cannot be launched as documented. Half a day.
4. **Fix persistence properly**: save only on write (or debounce ~500 ms), write to `*.tmp` then rename to keep a backup of the previous file, and honour `MAINTAINX_DB_PATH` in the launcher. **2–3 days** because it touches the request path (`execute()`/`touchLastSeen`) and needs the app re-tested.
5. **Remove the demo seed on first run** (default `demo1234` logins, `seed.ts:14-24`) and add a first-run "create admin" flow. 1 day.
6. **Fix the 500s**: catch database constraint errors and return 400 (`routes/equipment.ts:48-61`), validate `equipment_id` on fault create (`routes/faults.ts:75-104`). 1 day.
7. **Delete the ~55 MB of duplicate assets** and the Netlify/Scan/Sites/Chatbot/Register dead weight (see §5). 2–3 days of careful deletion — and it's the deletion that has the highest chance of breaking something, with no tests to catch it.

## Rough effort to a reliable, lean version

Two paths, same target, for a beginner using AI assistance and 5–10 focused hours a week:

### Path A — Build on this repo: **≈ 5–7 weeks (50–70 hours)**
Roughly: 2–3 days for the persistence/printer-safety fix; 1 day boot fix + Windows launcher; 1 day security (secret, registration, demo users, revoked tokens); 1 day validation/error handling; 2–3 days deleting and repairing (you will break auth at least once — see the three copies); 1.5–2 weeks for the **recurring-maintenance feature** (new table, new routes, new page, due-date job, reminders — the one thing you actually asked for); ongoing: every future field change touches 5 files with no test safety net. Steepest risk is not any single fix, it's that you're maintaining a codebase whose "shape" you didn't choose.

### Path B — Rebuild from scratch (recommended): **≈ 1.5–2 weeks (15–20 hours)**
Build **one process, one folder, one page per feature**:
* Node + Express in **plain JavaScript** (`type: module`, no build step), `node:sqlite` or `sql.js` behind a tiny wrapper — the only thing that matters is **prepare/step, not per-request `fs.writeFileSync`**.
* One `index.html` + one `app.js` using `fetch` and template literals; no React, no router, no TypeScript compiler. You already know basic web concepts — this is 20 lines to learn.
* Copy the good ideas from SIAI explicitly: its **SQL schema** (`database.ts:48-136` is a decent starting data model), its **`lib/auth.ts`** scrypt/token helpers (30 lines, correct), and its **look** (the Tailwind palette in `tailwind.config.js:9-49` and card styles will make the result look just as good for near-zero effort).
* Add `equipment`, `work_orders`, `parts`, `pm_schedule(equipment_id, interval_days, last_done, next_due)` with a query for "due in N days". Reminders: a "Due soon" page + a `.bat` on the Windows Task Scheduler. No HTTPS needed.
* Effort split: 3 days schema + API; 3 days UI; 2 days auth; 2 days PM + reminders; 2 days testing on a real Windows box. The result is a repo whose entire surface you wrote — when you add a field next month, it's one line of SQL, one line of form HTML and one `INSERT` change.

**Bottom line.** Keep the repo as a **reference** (it has a good schema, a correct password hash, and a nice look), not as a base. If you decide to keep it anyway, do items 1–3 above before you put it on a factory machine.

# Phase 15 — Find it: search that composes, files that match

## Goal

A workshop with two hundred machines could only be read by scrolling. This phase adds
one search box per list — work orders, machines, history — that composes with the
filters that already existed, and makes the CSV exports obey the same box.

## Decisions

* **One filters module.** `workOrderFilter` and `partsFilter` moved out of `server.js`
  into `filters.js`, next to the new `equipmentFilter` and the history filter (which
  absorbed `history-query.js`). There is now exactly one place that answers "which
  rows", and both the list route and the export route call it.
* **One query builder per screen.** `workQuery()` in `app.js` and `historyQuery()` in
  `history.js` build the query string for the list *and* its download. A download that
  assembled its own parameters is how a file stops matching the screen.
* **Wildcards are escaped.** `%` and `_` are LIKE's own syntax, so searching for `50%`
  would have matched everything. `likeParam()` escapes them and the queries say
  `ESCAPE '\'`.
* **Case-insensitivity** comes from SQLite's LIKE over ASCII, not from a `LOWER()`
  wrapper — fewer moving parts, and the behaviour is asserted rather than assumed.
* **Debounced at 150 ms.** One request per pause in typing, not one per keystroke.
* **Four empty states now.** "Nothing matches *x*" is a different sentence from
  "there is nothing here", on all three screens.

## Proof

Eleven new assertions (215 → 226), and three mutations, each caught by the assertion
written for it:

| Defect | Caught by |
|---|---|
| Wildcard escaping removed | `a percent sign searches for a percent sign` — 4 rows matched |
| Search clause removed from the work-order filter | six assertions, including the export |
| Export ignores `q` while the screen obeys it | `the work-order export applies the same search as the screen` — 4 rows vs 1 |

The last one is the point of the phase: it is the mutation that produces a file which
disagrees with the screen, and it fails loudly.

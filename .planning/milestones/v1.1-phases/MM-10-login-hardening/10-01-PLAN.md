# Plan 10-01: A source that guesses is made to wait

## Threat Model

| ID | Threat | Severity | Mitigation | Verified by |
|---|---|---|---|---|
| T-10-01 | Password guessing over the LAN, unthrottled | high | Threshold on failures per source per window | 10-01-01 |
| T-10-02 | The throttle becomes a denial of service: an attacker locks the admin out | high | Keyed on source, derived from timestamps, no stored lock; expires by arithmetic | 10-01-03 |
| T-10-03 | The throttle leaks which email addresses exist by behaving differently for unknown users | medium | Unknown email is an ordinary failure and is counted identically | 10-01-04 |
| T-10-04 | A spoofed `X-Forwarded-For` mints unlimited identities and bypasses the throttle | high | The header is not read; the socket address is used | 10-01-05 |
| T-10-05 | The failure map grows without bound | low | Pruned on write to the window; a source with no recent failures is deleted | 10-01-06 |

## Tasks

### Task 1: `starter/throttle.js`

A module with no knowledge of HTTP:

```js
createThrottle({ threshold, windowMs, maxWaitMs, now })
```

Returns `{ check(source), fail(source), reset(source) }`.

- `check(source)` → `{ blocked: false }` or `{ blocked: true, retryAfter }` in
  seconds, rounded **up** so a client never retries a millisecond early.
- `fail(source)` records a timestamp and returns the current blocked state.
- `reset(source)` deletes the entry.

`now` is injectable and defaults to `Date.now`, so expiry is testable without
sleeping. Failures older than `windowMs` are dropped on every call, which both
computes the answer and bounds the memory (T-10-05).

The wait escalates with the failure count but is capped, so an attacker gains
nothing by continuing to hammer — the cap is the window, which is the same wait
AUTH-03 already requires to be finite.

**Acceptance:** a simulated clock advanced past the window reports
`blocked: false` with no reset call. This is the whole of AUTH-03.

### Task 2: wire it into `POST /api/login`

**File:** `starter/server.js`

Before verifying credentials, `check()` the source; if blocked, return **429**
with `{ error, retry_after }`. A human message stating the wait is AUTH-01 — the
number alone is not a message.

On failure, `fail()` the source. The existing 401 body is unchanged, so nothing
is revealed about whether the email exists (T-10-03): an unknown email and a
wrong password take the same path.

On success, `reset()` the source. That is AUTH-02, and it matters for the
workshop: someone who mistypes four times and then gets it right is not one
attempt away from being locked out for the afternoon.

The source is `req.socket.remoteAddress`, with IPv4-mapped addresses
(`::ffff:1.2.3.4`) normalised so one client cannot appear as two.

**Acceptance:** 5 wrong attempts then a 6th → 429 with `retry_after`;
4 wrong then 1 right then a wrong one → 401, not 429.

### Task 3: assertions

**File:** `starter/scripts/smoke-test.js`

- the 429 arrives on the threshold + 1 and names the wait
- the message states a number of seconds
- a correct password after fewer than the threshold failures still works
- after a successful login the count is back to zero (assert the *next* wrong
  attempt is 401, not 429)
- a different source is unaffected while one is blocked — proved by the
  unit-level injectable clock rather than by spoofing a header
- an unknown email is counted the same as a wrong password
- `X-Forwarded-For` changes nothing
- with the clock advanced past the window the throttle allows the attempt again

The last one cannot be done through HTTP without waiting 15 minutes, so the
throttle module is imported directly by the test and driven with a fake clock.
That is the point of Task 1's injectable `now`: AUTH-03 is asserted as a fact
about arithmetic, not as a claim about a timer.

**Acceptance:** every assertion fails when its defect is reintroduced.

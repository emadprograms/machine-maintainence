# Plan 7-02: Per-part reorder level

## Objective

Replace the hardcoded `p.qty < 5` in `public/app.js` with a per-part threshold, migrated onto
existing databases through the established `ensureColumn()` mechanism.

## Tasks

### Task 1: Schema + migration
**File:** `starter/db.js`

Add `reorder_level INTEGER NOT NULL DEFAULT 5 CHECK (reorder_level >= 0)` to the `parts`
`CREATE TABLE`, and `ensureColumn('parts', 'reorder_level', 'INTEGER NOT NULL DEFAULT 5')` beside
the existing calls. Default 5 preserves today's implicit behaviour, so no existing part changes
meaning on upgrade.

**Acceptance:** starting against a pre-existing database logs `migrated: added parts.reorder_level` exactly once; a second start does not log it.

### Task 2: Accept and validate `reorder_level`
**File:** `starter/server.js`

Include `reorder_level` in `POST /api/parts` and `PUT /api/parts/:id`, defaulting to 5 on create.
Validate it the same way as `qty`: non-negative integer or 400.

**Acceptance:** creating without the field yields 5; `{"reorder_level": -2}` returns 400.

### Task 3: Badge logic and the form field
**Files:** `starter/public/index.html`, `starter/public/app.js`

Replace `p.qty < 5` with `p.qty <= p.reorder_level`. Keep the existing precedence: `qty <= 0` is
red "out", then the amber low-stock badge, otherwise the plain quantity. Add a "Reorder at" input
to the add form and to the inline edit row.

**Acceptance:** a part with `qty: 5, reorder_level: 5` shows amber; `qty: 5, reorder_level: 4` shows the plain quantity.

### Task 4: Smoke assertions for PART-05
**File:** `starter/scripts/smoke-test.js`

- create a part without `reorder_level`, assert it reads back as 5
- create a part with `reorder_level: 2, qty: 2`, assert the API exposes both and the boundary is inclusive
- assert two parts at the same `qty` with different levels carry different `reorder_level` values (the UI rule is then a pure function of that)
- assert `{"reorder_level": -1}` is refused

**Acceptance:** new checks PASS; the suite stays green end to end.

## must_haves (goal-backward)

1. Old database files keep working — proven by the migration assertion
2. The badge is driven by data, not a constant — proven by two parts differing at equal quantity
3. The boundary is inclusive — proven by the `qty == reorder_level` case
4. New input is validated like the old input — proven by the 400 assertion

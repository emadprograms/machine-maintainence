# Plan 9-01: Mark done honours the date

## Threat Model

| ID | Threat | Severity | Mitigation | Verified by |
|---|---|---|---|---|
| T-9-01 | Data integrity: an unparseable date silently becomes a different date, corrupting the maintenance schedule | high | Strict `YYYY-MM-DD` parse with a calendar check (rejects 2026-02-30); 400 naming the field | 09-01-02 |
| T-9-02 | Data integrity: a future date pushes `next_due` past a cycle that never happened | medium | Explicit refusal with a reason | 09-01-03 |
| T-9-03 | Injection: the date concatenated into SQL | high | Bound parameter to `date(?, ...)` as today; the value never reaches the SQL string | 09-01-02 |

## Tasks

### Task 1: Populate `req.body`
**File:** `starter/server.js`
In `route()`, read the body once for non-GET requests and assign `req.body`, so handlers no longer
have to call `readBody` individually for optional fields. Keep `readBody` available for handlers
that want the parsed object directly (they are unchanged). This kills the class of bug where an
optional field reads `req.body?.x` and is silently `undefined`.

Care: `readBody` rejects on malformed JSON. Adding a second read of the same stream is impossible
(a request body can only be consumed once), so `route()` must be the single reader when it does
this. Simplest correct shape: `route()` consumes the body and sets `req.body`, and handlers use
`req.body` instead of calling `readBody` — with `readBody` kept exported for compatibility during
the change and all call sites switched in the same commit.

**Acceptance:** the whole suite still passes; `req.body?.on` in the PM handler is now a real value.

### Task 2: Strict date parsing
**File:** `starter/server.js`
`parseDay(raw)` returning `{ value } | { error }`: must match `^\d{4}-\d{2}-\d{2}$` and round-trip
through `Date` so `2026-02-30` is rejected. Reused by the PM handler.

**Acceptance:** `2026-02-30` → 400; `2026-1-5` → 400; `2026-11-05` → accepted.

### Task 3: Honour, refuse and bound the date
**File:** `starter/server.js`
`POST /api/pm/:id/done` takes `on`. Absent → today (unchanged default). Present → validated,
refused if after today, refused if before `last_done`. Response includes the new `next_due`.

**Acceptance:** `{"on":"2026-01-15"}` stores `last_done=2026-01-15` and `next_due=2026-02-14` for a
30-day interval. Not "returns 200" — the stored values are the assertion.

### Task 4: Assertions that prove the value is used
**File:** `starter/scripts/smoke-test.js`
- send a past date, assert `last_done` equals it and `next_due` equals date + interval
- send a future date, assert 400
- send `2026-02-30`, assert 400 and that `last_done` did NOT change
- send a date before `last_done`, assert 400
- send no date, assert `last_done` is today

**Acceptance:** all green; the first one would fail against v1.0 code.

# Plan 7-01: Parts become maintainable

## Objective

Close the one-way ratchet on `parts.qty`. v1.0 shipped create-and-consume; this plan adds the
missing update and delete, with an in-use guard that explains itself.

## Threat Model

| ID | Threat | Severity | Mitigation | Verified by |
|---|---|---|---|---|
| T-7-01 | Mass-assignment: a client PUTs a field it should not control (e.g. `id`) and rewrites the row identity | medium | Handler enumerates the fields it accepts; `id` is taken from the URL only | 07-01-02 |
| T-7-02 | Injection via numeric fields — `qty` used to build SQL | high | All writes use bound parameters through `run(sql, ...params)`; `qty` is coerced with `Number()` and validated before use | 07-01-01 |
| T-7-03 | Destructive action by a technician deleting stock records with history | medium | In-use guard refuses deletion when `work_order_parts` rows exist | 07-01-04 |
| T-7-04 | Unbounded input causing a 1 MB body or a huge integer | low | `readBody` caps at 1 MB; `qty` is bounded by an explicit sanity limit | 07-01-01 |

## Tasks

### Task 1: `PUT /api/parts/:id` — edit stock and descriptive fields
**File:** `starter/server.js`

Accept `qty`, `name`, `reference`, `supplier`, `unit_price`. Read the current row first and fall
back per field (`b.name ?? before.name`) following the `PUT /api/equipment/:id` pattern, so a
partial update cannot blank an untouched field. Validate:
- `name`, if supplied, must be non-empty after trim
- `qty`, if supplied, must parse as a non-negative integer (`Number.isInteger` after `Number()`) and be below 1,000,000
- `unit_price`, if supplied and not null, must be a finite non-negative number

Return the updated row.

**Acceptance:** `PUT` with `{"qty": 50}` returns 200 and the row shows 50; a second `PUT` with only `{"name":"X"}` leaves `qty` at 50; `{"qty": -1}` and `{"qty": "abc"}` return 400.

### Task 2: `DELETE /api/parts/:id` with the in-use guard
**File:** `starter/server.js`

Count `work_order_parts` rows for the part. If any exist, join to `work_orders` and return 400:
`This part was used on: <titles>. Remove it from those jobs first.` Otherwise delete and return
`{ ok: true }`. A missing part returns 404.

**Acceptance:** deleting an unused part returns 200 and a subsequent `GET /api/parts` omits it; deleting a consumed part returns 400 whose message contains the work-order title and does not contain the string `FOREIGN KEY`.

### Task 3: Parts screen — edit and delete affordances
**Files:** `starter/public/index.html`, `starter/public/app.js`

Add an actions column to the parts table with Edit and Delete buttons. Edit switches the row's
cells to inputs prefilled from the row, with Save and Cancel; Save sends a `PUT` then reloads the
list. Delete uses `confirm()` and a `DELETE`. No modal, no new page.

**Acceptance:** clicking Edit shows prefilled inputs; Save persists; Cancel restores the read-only row; Delete on an in-use part surfaces the server's message via `alert(e.message)`.

### Task 4: Smoke assertions for PART-01 … PART-04
**File:** `starter/scripts/smoke-test.js`

Add assertions after the existing phase-4 consumption block, reusing its seeded part and
work-order fixture:
- restock raises stock and the value is returned
- partial update does not blank an untouched field
- negative and non-numeric quantity rejected with 400
- deleting an unused part succeeds and the list shrinks
- deleting the consumed part returns 400, the message names the job, and no `FOREIGN KEY` text leaks

**Acceptance:** the suite reports the new checks as PASS; total count rises from 47.

## must_haves (goal-backward)

1. `qty` can increase — proven by a restock assertion, not by the route existing
2. Fields are correctable — proven by a partial-update assertion
3. Deletion works when safe — proven by a list-length assertion
4. Deletion is refused when unsafe, with an actionable message — proven by asserting the message content
5. Invalid input is rejected, never coerced — proven by 400 assertions
